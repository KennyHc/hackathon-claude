How we reconcile 200,000 bank lines

For every bank line, our pipeline says which open invoices it settles and for how much, or what kind of movement it is, and flags anything that doesn't add up. This guide walks through the patterns we found in the data and the rule we built for each, with the numbers behind every claim.

1 · The task in one picture

One bank line in, a set of settled invoices out

A fictional industrial group (17 companies, about 50 bank accounts, 11 currencies) books money in and out. Each bank line either settles open items (customer and supplier invoices and credit notes, each for an exact amount) or is something else (bank fees, payroll, a cash-pool sweep…). When the amounts don't match, the row carries an exception that says why.

2 · How the score works

Pairs carry half the score, so big lines weigh the most

Score = 100 × (0.5 · allocation F1 + 0.3 · transaction accuracy + 0.2 · exception macro-F1). An amount counts as right if it is within max(0.01, 0.5 %) of the answer.

50Allocation F1Counted over (bank line, item) pairs. A batch with hundreds of rows weighs as much as hundreds of simple payments.
30Transaction accuracyCounted over lines. A line is right only if every row on it is right.
20Exception macro-F1The 10 codes averaged equally: each is worth up to 2 points.

One disputed short payment ≈ 98 ordinary payments

An ar_short_dispute line settles about 98 invoices on average (1,067 lines hold 104,691 pairs). Getting one wrong costs as much allocation F1 as missing 98 one-invoice payments.

Rare exceptions weigh as much as common ones

Macro-F1 averages the codes, so the 400 overpayments in val count as much as the 15,624 early-payment discounts.

What that means for strategy

A wrong claim loses the pairs, the line and possibly an exception. An unclaimed line loses only the line. So every matcher claims a line only when it is sure, and we would rather leave a line for the classifier than guess. That is why submitted pairs run at 99.9 % precision.

3 · Where the points are

Ten segments hold more than half of the score

The answer key tags each bank line with a case type (a segment, 71 of them in val). For each, we computed how many points it would add going from 0 % to 100 % right. This table set the order in which we built matchers.

4 · Architecture

Most certain evidence first, and each line claimed once

Eleven matchers run in a fixed order. Each recognises one family of cases and claims whole lines it is sure about; a line claimed by one matcher is never touched by a later one. Open amounts are updated in booking order, so later matchers see what earlier ones consumed. What is left goes to the classifier.

in

Ingestion

Parses each bank's statement format (camt.053, Norma 43, MT940…) into one bank-line table with direction, absolute amount, EUR amount, payer name and the document-like tokens in the text. Builds the open-item list (customer and supplier invoices and credit notes) and caches the text of the invoice PDFs (about 131k in TRAIN). Reads side files from the neighbouring period too. It also extracts the PDF text itself (ingestion/pdftext.py); before that there was no PDF cache for FINAL, and PDF clauses and PDF remittance advices would have been silently empty.

Classifier for lines that settle nothing

One logistic regression over 22 classes (ITEM + 21 categories) labels the 23,110 unclaimed lines. It also gives p_items, the probability a line settles invoices at all, which can veto a matcher's claim and decides UNIDENTIFIED.

x

Exception rules

POLICIES §3 written as code: discounts, withholding, bank charges, FX, partials, overpayments. Labels set by evidence matchers (PDF clauses, advices, batch files, payment runs) are kept; the rules only fill in the rest.

✓

Integration

Merges matcher rows and classifier labels, validates the file (every line present, format rules), scores it locally and writes submission.csv.gz. Safety nets: a crashing matcher is skipped, the classifier falls back to a baseline, and FINAL uploads need an explicit flag. integration/final.sh runs FINAL end to end in one command and integration/drift.py compares the result with LIVE before anything is uploaded.

5 · Patterns and solutions

Twelve patterns, twelve rules

Each chapter shows what the pattern looks like in the bank text (real lines from the synthetic val data), how we detect it, and how well it works on val. Chapters follow the order the pipeline runs in.

5.1 matcher 1 · payment_runs

Supplier payment runs

Our own companies pay suppliers through payment-run files. A run can be paid as one debit per beneficiary (transfers), one debit for the whole file (aggregated), or one debit per maturity date (confirming). One of these debits can hold hundreds of invoices.

  1. Link the debit to a unit of a run file: by end-to-end ID or run ID when the bank shows it (camt.053).
  2. Otherwise (Norma 43, MT940): same account, amount, booking date shortly after execution, plus beneficiary name.
  3. Every document in the unit becomes a row; items of ES01/ES02/PT01 paid by the ES00 payment factory stay with the subsidiary.
  4. An end-to-end ID ending in “D” marks a duplicate transfer → DUPLICATE_PAYMENT.

Segments at 100 %: ap_payment_multi, ap_payment_single, ap_paid_by_holding, ap_direct_debit, ap_partial, ap_credit_note_netted. ap_fx 99.8 %, ap_factored 99.2 %, ap_confirming 98.4 %. Rejected transfers: 168 of 171 claimed at 100 %.

5.2 matcher 2 · dd_batches

Direct-debit batches and returns

We collect from many customers at once (SEPA, BACS, ACH, BECS) and the bank credits the batch total as one line. Weeks later some receipts bounce back as separate debits carrying the mandate reference.

  1. Batch credit: same account, amount = batch total, date −2/+6 days. Every receipt in the batch file becomes a pair.
  2. Return: a debit with a mandate reference goes to the latest earlier receipt with that mandate and amount → RETURNED.
  3. The time window depends on the SEPA reason code: MD06 (“refund request”) 14–80 days, others 1–20.
  4. Re-presented: a customer whose debit bounced pays by transfer instead; each item keeps a timeline of collections and returns.

Line accuracy: ar_dd_batch 99.9 %, ar_dd_returned 99.5 %, ar_dd_represented_transfer 98.1 %. RETURNED F1 0.994.

5.3 matcher 3 · cards_cheques

Card settlements and cheque deposits

The card acquirer pays out the day's web orders as one credit, net of its fee. Cheques arrive in deposits or US lockboxes, often with a truncated or missing stub reference.

  1. Card settlement: credit on the settlement account = Σ net of the settlement file (merchant ID and date in the text).
  2. Each order is cleared at its gross amount with no exception. The acquirer fee is contractual, not a short payment.
  3. Cheque deposit: credit = deposit total (deposit ID in the text); each cheque goes to its invoice by stub, drawer and amount.
  4. Chargebacks and returned cheques → RETURNED on the original invoice.

Line accuracy: cards, cheques, chargebacks and returned cheques all 100 % on val.

5.4 matcher 4 · remittance

Remittance advices

Big customers pay dozens or hundreds of documents with one transfer and send an advice listing each invoice, what they paid and any deduction. This is where the biggest lines live: ar_short_dispute lines settle 98 invoices on average, up to 903.

  1. Parse four formats: CSV (, or ;), PDF text in English and Spanish, email text, XLSX; US and European number formats.
  2. Resolve each advice line to our item by number (also without prefix), else by amount and date inside the payer's group.
  3. Link the receipt by payment reference, else by entity + amount = advice total around the payment date.
  4. A deduction with a dispute reason → SHORT_DISPUTE (amount = paid); “SETTLEMENT <doc>” later pays the remainder.
  5. Read the neighbouring period's folder too: advices for late-June payments sit in the next period. That recovered about 10 % of 1:N lines.

Drift handled: from Aug/Sep 2025 one customer sends a new “Voucher” XLSX holding only the last 6 digits of our number. All 6,889 LIVE advices parse; 98.1 % add up to their stated total.

5.5 matcher 5 · pdf_cases

Clauses printed in invoice PDFs

Some invoices are paid in a way only the PDF explains: in instalments, minus a guarantee retention (released later), minus an advance already paid, or cancelled and replaced by another invoice. We surveyed all 131k TRAIN PDFs: clauses are only ever worded in Spanish or English, and clause dates are always dd/mm, even on US documents.

  1. Extract clauses and check them: instalments sum to the total, retention + net = total, advance + net = total.
  2. Walk the bank lines in booking order, keeping a running open amount per clause item.
  3. The cash must fit the clause to the cent. Which instalment: “k/n” in the text, else the only unpaid one of that amount, else the one whose due date passed most recently (right 99.9 % of the time).
  4. Advance deductions stay PARTIAL even when the cash equals the open amount; the generic rules may not override evidence labels.

Recall on val: instalments 99.2 %, retentions 98.5 %, releases 99.3 %, advance deductions 98.9 %, replaced invoices 90.5 %, credit notes paid out 100 %.

5.6 matcher 6 · refs

Invoice numbers in noisy bank text

The largest segment, ar_ref_noise (42,462 lines, up to 12.7 points), is customers citing our invoices badly: prefixes dropped, numbers cut off by the bank's field width, one digit wrong, two digits swapped, or several numbers run together.

  1. Tokenise text and remittance info; re-join numbers split across Norma 43 | fields; drop amounts, IBANs and bank IDs.
  2. Find candidate customers from tokens that hit items: exact, suffix (number without prefix), prefix (truncated), or one edit / transposition.
  3. Within that customer's open items only, pick one item per cited token so that Σ invoices − credit notes = cash ± 0.01.
  4. Else complete with uncited open items (credit notes first), else explain the gap with an exception.

Second round: trying related credit notes first lifted ar_1toN_credit_note 0.60 → 0.749, ar_n_to_m 0.53 → 0.728, ar_fx 0.53 → 0.874 (with subset-sum changes).

5.7 matcher 7 · subset_sum

Who paid, and which invoices add up

Many receipts cite nothing useful. Then we need two answers: which customer paid, and which of its open invoices the amount settles. Third parties muddy the first: parents pay for subsidiaries, collection agencies pay under a file number (EXPTE), confirming banks pay on behalf (ORD.).

  1. Payer: IBAN against the customer master and IBANs learned from TRAIN; payer name cut out by per-format patterns (/ORDP/, ORD., EXPTE, POR CTA DE, SPEI…), compared on letters and digits only so truncated names still match.
  2. Pool: that customer's open items in the line's entity and currency, issued by the booking date, minus what earlier matchers and lines took.
  3. Search: one invoice, one net of its discount or withholding, then subsets. If the direct payer has none, try the group's other customers.
  4. Guard: claim only if exactly one customer has a solution and the expected number of coincidental matches is ≤ 0.3.

Payer knowledge on LIVE: 86,003 name aliases and 5,483 learned IBANs, learned only from lines before the window.

5.8 matcher 8 · same_amount

Same-amount invoices

Service customers pay a fixed monthly fee, so the same customer has several open invoices of identical amount. The amount alone cannot tell them apart.

  1. A month named in the text (“SERVICE MAY 2025”, “MANT. MAYO 25”, “SERVICIOS MAYO”) picks the invoice for that service month, which is issued at the start of the following month.
  2. Otherwise take the oldest open one (first in, first out).
  3. Runs inside the same chronological pass as subset-sum, so an invoice consumed by one line is never offered to a later one.

Unfixable noise: when a customer pays two same-amount invoices on the same day, which line gets which invoice is random in the answer key. About 140 val errors come from that.

5.9 matcher 9 · short_payments

Short payments and overpayments

A receipt a little below or above one open invoice of the payer. The gap has a cause, and each cause has its own exception code and its own fingerprint.

  1. Only receipts no earlier matcher claimed, with a resolved payer and exactly one open invoice that the gap explains.
  2. SHORT_BANK_CHARGES: a small fixed gap taken by intermediary banks on international wires.
  3. SHORT_WITHHOLDING: 1.25 %, 1.5 % or 10 % withheld tax, only for MX, BR and MA customers.
  4. OVERPAYMENT: only if the excess is a round amount (1 to 200) or exactly +1 % or +10 % (chapter 6).

Exception F1: SHORT_BANK_CHARGES 0.368 → 0.937, OVERPAYMENT 0.575 → 0.992.

5.10 matcher 10 · ap_refunds

Supplier refunds

Money flows the other way: a supplier refunds one of its credit notes to us. The incoming line settles the supplier credit note (APC) for its open amount, with no exception.

  1. An incoming line equal to an open supplier credit note of that entity, in the same currency.
  2. The credit note is pointed to by its number (supplier numbering, with or without prefix), the invoice it credits, or the supplier's IBAN or name.
  3. Exactly one credit note must qualify.
  4. Texts saying “PAGO DOBLE / DOUBLE / TWICE” are left alone unless they cite a credit-note number: those refund a payment we made twice, a different category.

5.11 matcher 11 · duplicates

Duplicate payments

A customer pays an invoice that is already settled. Runs late, on credits still unclaimed after the evidence and amount matchers.

  1. An earlier line 0–14 days before paid exactly that one invoice, in full, for the same amount, from the same payer.
  2. Any document number cited in the text must be that invoice.
  3. The customer must have no other open invoice of that amount; otherwise it is just next month's fixed fee.
  4. Duplicates never reduce the open amount: an early bug undid them as reductions, which caused 27 of 30 duplicate misses on the sample month.

5.12 matchers 12–13 · cn_bundles · sd_noadv

Big lines nobody could fully explain

Both run last, only on customer receipts every other matcher left unclaimed, and both may claim part of a line. A part-right line still scores pairs, and those lines were all wrong before.

  1. cn_bundles: the text cites some invoices; the payer's own credit notes net against them. Claim the whole set when exactly one completion adds up to the cash, otherwise only the cited invoices.
  2. sd_noadv: a bulk payment with no advice and no usable reference. Pick the one payer whose open invoices due around the date can cover the cash (or break a tie by IBAN).
  3. A logistic regression scores each of that payer's open invoices (days from due date to payment, invoice age, share of the cash, due-date rank, running total vs cash, partial number matches in the text; nothing payer-specific). Claim invoices with p ≥ 0.60 at full open amount, only if they cover at least 80 % of the cash.
  4. Trained across windows: the val model learns from the holdout and vice versa, and LIVE/FINAL use both. It shipped only after gaining on val, holdout and LIVE.

5.13 classifier · classification

Categories and UNIDENTIFIED

9.5 % of val lines (19,051) settle no item. Three categories dominate: BANK_FEES 9,718, UNIDENTIFIED 4,585 and CASH_POOL 1,554; the other 18 share 3,194.

  1. One logistic regression over 22 classes, with features from bank codes, text words, counterparty IBAN type, mentions of our own accounts, and “pair context”: an opposite movement on another of our accounts the same day, as in cash-pool sweeps and FX deals.
  2. Two deterministic overrides: reversal pairs (“ANULACION OPERACION INDEBIDA” with the wrong booking) and keyword rules for near-empty classes (TAX_REFUND has 4 examples in all of TRAIN, LOAN_DRAWDOWN 32).
  3. p_items vetoes matcher claims on lines that look like no-item lines: on val it removed 18,157 lines, of which only 19 were real item lines.
  4. An unclaimed receipt becomes UNIDENTIFIED only when p_items < 0.97 (chapter 6).

6 · Exception rules

The answer key is very literal, down to the cent

The labels follow POLICIES.md exactly, including how amounts are written and how they are rounded. Copying those details took several exception F1 scores from about 0.1–0.6 to above 0.93. Fed the true items and amounts, our rules library scores macro-F1 above 0.98 on every code it decides; the remaining exception errors come from matching.

Amount convention

Write the invoice, not the cash, when the gap is explained

When an invoice is fully cleared with an explained shortfall (discount, withholding, bank charges, FX), the row's amount is the invoice's full open amount. For a real partial payment it is the cash applied. Getting this wrong costs the pair, the line and the exception at once.

Rounding

Half-up for deductions, truncation for partials

Discounts and withholding are rounded half-up to the cent. Python's default round() is banker's rounding and reproduced only part of them. Partial payments are truncated: a third of an invoice is cut, not rounded.

Overpayment fingerprint

Every real overpayment is round

In the answer key, an overpayment is always the invoice plus a round amount (1 to 200) or exactly +1 % or +10 %. Our check overpayment_plausible keeps only those. OVERPAYMENT F1 went to 0.992.

The UNIDENTIFIED trade-off

Flag only what looks like nobody's invoice

First version: every unclaimed receipt was UNIDENTIFIED. Recall 1.0, precision 0.442 (5,777 false positives), F1 0.614. A matcher miss is a wrong line either way, so flagging it only added a false positive. Flagging only when the classifier gives p_items < 0.9 (with dropping a bad fallback) took val from 90.04 to 90.81. A later scan of the threshold found a flat plateau with the same best value, 0.97, in both windows, so we moved there: UNIDENTIFIED F1 0.971 on val.

7 · Why you can trust the number

No leakage, an untouched holdout, and a real LIVE score

Only two components learn from the answer key, both cut by date. No matcher reads it. The one random draw uses a fixed seed and no LLM is called anywhere, so the same input gives the same file.

The start-state leak, found and fixed

To make Jan–Jun 2025 look like LIVE we must rebuild which invoices were open on 1 Jan. Working backwards from the end-of-June list dropped 21,825 invoices (7.94 %) that were open in January but later cancelled without a payment. In LIVE those stay as distractors, so removing them made matching look easier.

Fix: rebuild from payments before the window only. Cost of the leak: 0.04 points (96.40 → 96.36).

LIVE is 0.4 below val, and nearly all of it is recall

Precision is the same: 0.9966 on LIVE against 0.997 on val. Overfit rules make confident wrong claims, which would show up as lower precision. Here we simply find fewer lines and exceptions, which is what drift looks like.

90 % of the val gain showed up on LIVE

The same code change (v1 → v2) gained about 2.06 points on val and 1.85 on LIVE. The afternoon round (v3 → v6) gained +0.38 on val, +0.41 on the holdout and +0.80 on LIVE (one fix had cases only in LIVE). A rule set tuned to val quirks would not transfer like that. Every check is in OVERFITTING_CHECKS.md in the worktree.

The remaining risk: drift

Val and hold are both inside TRAIN, so neither tests the changes POLICIES §6 announces. Only LIVE and FINAL measure them. Matchers that rely on learned payer aliases or bank-text formats are the most exposed.

  • 2025-09 · LIVEA big customer switches to a new “Voucher” remittance layout. Handled (chapter 5.4).
  • 2025-10-01 · LIVEBanco del Moncayo moves from Norma 43 to camt.053, so texts look different. The category model gives Oct–Dec the same no-item mix as Jul–Sep.
  • 2026-01-01 · FINALA new South African subsidiary: new entity, new bank, ZAR, its own invoice numbering, renamed on 2026-04-01.
  • 2026 · FINALCustomers are renamed, change banks and pay more slowly.

8 · Score progression

From 12.72 to 96.79

The jump came from building every side-file matcher in parallel; the last six points came from exception rules and a second wave of targeted matchers. Moving the UNIDENTIFIED threshold to 0.97 added 0.05, and an afternoon round (remittance FX and exception fixes, the cn_bundles matcher, then the sd_noadv ranker) another 0.38. On LIVE, our code scores 96.42, and 96.46 on main with a teammate's new classifier on top. The organisers' reference points: about 19 for a naive baseline and about 61 for well-worked rules.

9 · What's left, and what we learned

The remaining losses are genuinely ambiguous

Almost every remaining line error is a line no matcher claimed. Most are lines where several sets of invoices add up to the same amount, or disputed short payments with no advice anywhere. We left those unclaimed rather than guess.

Priority-ordered matchers that claim whole lines

Each matcher claims only what it is sure of, and later matchers see earlier claims. Precision stays at 99.9 % because nothing guesses on a line a more certain matcher could own.

Leave a line unclaimed rather than guess

A wrong claim loses pairs, the line and maybe an exception; a miss loses only the line. Every ambiguous matcher has a “unique solution only” guard.

Side files beat clever text matching

Payment runs, batches, card and cheque files, advices and PDF clauses resolve their cases at 99.6–100 % precision, and one line can hold up to 1,540 pairs.

Measure precision per method

ref_exact, written as an early catch-all, fell to 0 % precision on 201 lines once better matchers ran first. Per-method precision in the scorer made that visible, and we removed it.

Your validation set is code too

Rebuilding the start state went wrong three times, each time moving the local score. It needed the same scrutiny as the model.

Evidence beats generic rules

Exception labels from matchers that read documents are kept; generic rules only fill the rest. Without that, advance-deduction accuracy fell to about 0 %.

Parallel agents need separate outputs

Agents running partial matchers overwrote a shared file and produced a bogus 36.48. Partial runs now write their own file.

Ownership gaps lose points silently

Rejected supplier transfers were left to nobody after two conflicting instructions. Turned back on: 168 of 171 at 100 %.

Ideas we have not tested yet

Break subset ties in ar_ref_noise with due-date order or the payer's habitual patterns; a deeper credit-note-aware search for truncated multi-invoice texts; track partial-payment state across matchers so refs can tell a remainder from a first partial (ar_n_to_m).
